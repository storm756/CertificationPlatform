# Settled decisions

These are product decisions. **Build to them.** If one seems impossible or harmful, raise it. Don't work around it.

| # | Decision |
| --- | --- |
| D1 | Certificate result = **50% module assessments + 50% final exam**. This is the whole result (it replaces the booklet's 20/30/30/20). |
| D2 | **Learning is never locked.** Learners see their % per module and for the final. Final pass mark: **50%**. Module pass mark: **50%**. |
| D3 | **Unlimited attempts; the best counted attempt per part counts.** A timer is shown but not enforced (a setting exists for later). |
| D4 | Learners **self-register with their own email** and pick a batch from a dropdown. |
| D6 | Practicum, portfolio and viva come **later**. Don't build them now, but don't design anything that blocks adding them. |
| D7 | Languages: **English, Hindi, Marathi, Gujarati**. The team reviews every translation. |
| D8 | Custom Django platform. **No Moodle.** |
| D9 | **Registration is closed by default**, for every batch including the catch-all "Open Enrolment" pool. Only a batch that a mentor or admin has opened (optionally for a time window) accepts sign-ups. The server re-checks this on submit. |
| D10 | Certificates are **English only, delivered on the website** (no email). Each batch has an **auto-issue** switch; otherwise the mentor approves batch by batch. Email (Brevo, 300/day) is used **only** for verification, password reset and guardian consent. |
| D11 | Staff can add content (Word, text, images, PDF, video links) and questions (form or spreadsheet) **without developers**. **Every module = 100 marks**, split across its assessment parts (today MCQ 50 + Interactive 50). |
| D13 | After an assessment: score, ✓/✗ per question, and a **hint**. **Never the correct option.** Full worked answers appear only in practice. |
| D14 | Final exam: a random draw per learner, questions and options shuffled, per-module results shown as **bands** (strong / OK / needs work), no answers shown. A wait between attempts is a setting, **off** by default. |
| D15 | A module submission counts toward unlocking the final only if **every question was answered**. |
| D16 | **Minimum age 16.** 16–17-year-olds need **guardian consent** (by email) before activation and get **no time-on-task tracking** (DPDP). The consent method is pending confirmation by CyberPeace legal, so keep it isolated in `GuardianConsent`. |
| D17 | **The certificate name is typed at registration** and shown as a preview. After that only a mentor or admin can change it. |
| D18 | **Films are on YouTube** (unlisted, `youtube-nocookie.com` embed). An MP4 upload is the fallback. No video processing on our server. |
| D19 | Repo `storm756/CertificationPlatform`, domain **cyberfirstresponse.io** (staging: `staging.cyberfirstresponse.io`). The old 405 MCQs are public, so they go into the module-quiz and practice pools only. **The final pool is written fresh** by the content team. |
| D25 | **Safety gate:** an attempt containing a choice that would endanger a citizen (e.g. asking for an OTP) is shown with its score but **never counts**. |
| D20 | **Visual direction is the team's standalone frontend prototype** (cream header with both partner logos, navy hero, mustard primary button, Learn → Practise → Assess → Certify stages). It lives in `design-reference/frontend-prototype/` as the reference for every page. It is the look, not production code. |
| D21 | **No dark mode in v1.** Remove the prototype's night-mode toggle. One light theme only, to halve the design and testing work. |
| D22 | **Both repos stay public until launch.** Before the first batch, the old `csfr_Project` repo is deleted. Until then: no secrets, no question data, no answer keys in git. |
| D23 | **Programme name: Community Cyber First Responder, short form CCFR** (decided 10 Nov 2026). Code reads it from `settings.PROGRAMME_NAME` / `PROGRAMME_SHORT`, never hard-coded. The prototype says "CSFR" in places, and every one of those becomes CCFR. **The programme gets its own emblem** (wanted, design pending). Keep a slot for it in the header, on the landing page and on the certificate. The certificate's qualification title and its signatories are still open (STATUS.md). |
| D24 | **Assessments may be shown in Hindi, Marathi or Gujarati once a reviewer has approved that wording.** Until then they show in English (architecture §14). They are not English-only forever. |
| D26 | Module 10 is an ungraded capstone and stays Coming soon until its content is ready. The legacy 18-challenge mixed set is the separate ungraded practice mock. The six existing Module 8 crosswords make up its 50-mark graded Part B. Crosswords in other modules remain practice-only. |
| D27 | **A `tasks` service for daily jobs is allowed.** It runs on the web image with a `run_periodic` loop (every 10 minutes, jobs scheduled in Asia/Kolkata time, catch-up once after a restart). It is **not** a job queue: Redis and Celery stay rejected. Today's jobs are `purge_unverified` (Stage 1) and auto-submitting stale attempts (Stage 2). |
| D28 | **The certificate-number prefix comes from settings** (`CERTIFICATE_PREFIX`, today `CCIFR-<year>-<centre>-<serial>` as in architecture §12). The lead confirms the final prefix, qualification title, wording and signatories before Stage 7 (answered in D36). |
| D29 | **Only a person merges, deploys, or pushes to `main`.** Claude prepares branches and PRs; the builder reviews and merges them. `.claude/settings.json` blocks `deploy/deploy.sh`, `ssh` and `gh pr merge` for Claude, and branch protection on `main` requires a PR and a green CI (0 approvals, so the builder can merge her own PRs). |
| D30 | **The CCFR rename covers user-facing text only** (pages, emails, PDFs, page titles). Internal names such as the `csfr_owner` / `csfr_app` DB roles, container names and cookie or storage keys stay as they are. |
| D31 | **Final exams come from fixed exam sets, one per batch** (requested by the repo owner, 12 Nov 2026; **confirmed by the owner on 13 Nov 2026**, including "a correction to a released set is a new draft set"). Sets B and D are written fresh by the content team (D19). An **admin** assigns one released set to a batch (audited); mentors and learners cannot. The set supplies both exams: the **pre-test is its shared questions (2 per module, 18)** and the **final is all 50 of its questions**, including those 18, shuffled within the set and never mixed with another set. A learner's set and question versions are **frozen when their first programme exam starts**, so a batch move or reassignment cannot pair a Set B pre-test with a Set D final. A set is released only when its release checks pass (blueprint counts, 2 pre-test questions per module, single-choice, 1 mark, no reused or copied module/practice question). Until then learners see a clear "not available yet" state. This replaces the per-learner random draw and `is_anchor` tagging of §11 / D14's "random draw"; D14's shuffling, bands and no-answers rules stay. **A released paper is fixed:** release records the approved question versions, marks, formats and modules, and neither the app nor the database allows the set, its membership or those questions to change afterwards. A correction is a new draft set. Drafts are reconciled with the workbook by `import_final_sets` (rows can be held in reserve or rejected, never deleted). Questions already met in a module quiz, practice, a lesson check or an earlier version of any of those can never join a set. |
| D32 | **Attempt limit setting** (13 Nov 2026). Unlimited attempts stay the default (D3). Every assessment part and the final (`ProgrammeAssessment`) has an admin-editable **maximum attempts**; blank means unlimited. When set, the learner sees "N of M attempts used", and once the limit is reached Start is replaced by a clear message. Every attempt the learner started counts as used (in progress, submitted, auto-submitted or gated). The best counted attempt still counts. Changing the limit is audited. The server enforces it under the same per-learner lock that prevents two attempts at once, and an attempt already in progress is never cut off (it can always be resumed and submitted). The pre-test stays once only and takes no limit. |
| D33 | **Module 8 crosswords stay English** (13 Nov 2026). Module 8's graded Part B (the six crosswords, D26) shows in English in every language, also after Stage 8. The Module 8 page says so in the learner's language; the Hindi, Marathi and Gujarati wording needs the team's review (D7). |
| D34 | **Lessons need sign-in** (13 Nov 2026). Overrides the Stage 4 call "lessons are readable without signing in". Everything under `/learn/` (catalogue, modules, readings, films, handouts, practice checks, media and the `/learn/check` endpoint) needs a signed-in user. A signed-out visitor asking for a page goes to sign-in and then back to that page; a signed-out POST to a `/learn/` endpoint gets 403. Public pages stay public: landing, register, sign-in, help, privacy, terms, grievance and the future certificate verify page. Film and handout files are served only through `/learn/media/<id>/` to signed-in users (`Cache-Control: private`); the handout PDFs are no longer collected as static files. |
| D35 | **Films stay MP4 for now** (13 Nov 2026). YouTube (D18) comes later, and more films may be added. Django checks the sign-in and that the file belongs to a published unit, then hands the file to Caddy (`X-Accel-Redirect`), which serves it with range requests, `ETag` and `Last-Modified`, so a phone can seek without downloading the whole film and no Django worker is held for the download. Outside Caddy (development, tests) Django serves the file itself. |
| D36 | **Certificate decisions (answers D28; the lead, 13 Nov 2026).** **Title:** "Community Cyber First Responder (CCFR)" (long form, short form in brackets; built from `PROGRAMME_NAME` / `PROGRAMME_SHORT`). **Wording, one page, English:** CERTIFICATE OF COMPLETION / Community Cyber First Responder (CCFR); "This is to certify that **[certificate name]** has successfully completed the Community Cyber First Responder programme, conducted by the Department of Cyber Security, Shah & Anchor Kutchhi Engineering College (SAKEC), in collaboration with CyberPeace Foundation, and is awarded **Grade [X]**."; a line with Batch, Completed on and Certificate No.; the NSQF line; three signature blocks; the QR code with "Verify at <domain>/verify/<code>". **The grade only:** no percentages and no hours are printed (the snapshot still stores them, §12). **Signatories, left to right:** Dr. Nilakshi Jain, HOD, Cyber Security Department, SAKEC · Dr. Bhavesh Patel, Principal, SAKEC · Maj. Vineet Kumar, Founder, CyberPeace Foundation; kept in settings (`CERTIFICATE_SIGNATORIES`), not in the template. **Signature images are never in git** (D22): they are loaded from private storage on the server (`CERTIFICATE_PRIVATE_ROOT/signatures/`); a missing image prints the name and designation over a blank line. **Number:** `CCFR-<issue year>-<centre code>-<6-digit serial>`, e.g. `CCFR-2026-SAKEC-000001`; `CERTIFICATE_PREFIX = "CCFR"` (replaces "CCIFR"); the centre code is a per-batch field (2–6 capital letters or digits, admin-set, default `SAKEC`); one global serial from a database sequence, never reset per year and never reused. **Design:** a placeholder A4 landscape page in the look of `cert-front.jpg` until the final design; the template is self-contained so the final design is a template-only change; the emblem slot shows "CCFR" until the emblem exists (D23). **NSQF:** "NSQF level and credits shown after approval by the competent authority" until an admin turns `nsqf_approved` on (new issues only). **Issuing:** auto-issue is off by default per batch, so certificates wait for a mentor's approval (§12). **Safety:** each PDF is fixed at issue, so no real learner's certificate is approved before the signature images, the final design and the emblem are in. Mentors and admins see a warning while signature images are missing or `CERTIFICATE_DESIGN_FINAL` is off (a warning only; approving still works). |

D5 and D12 aren't used. Numbers are never reused.
